## 启用条件与能力边界

只有用户明确需要保存草稿时才接入。本能力不是默认生成项；没有草稿需求时，不主动要求用户选择，不添加草稿按钮、保存状态字段或额外过滤。字段默认值是独立能力，不以启用草稿为前提。

区分三个概念：业务 Record 草稿、正常保存但尚未发起审批的记录，以及筛选器、编辑器或聊天输入中的本地暂存。`UNSUBMITTED` 不能用来判断业务草稿。

Make 的 `isDraft` 是单次 Record 创建/更新选项。`true` 只跳过该次必填校验；它不持久化状态、不隔离查询、不阻止保存回调、不关闭关联同步或自动化，也不自动发起审批。类型、格式、选项、范围、唯一性、权限、锁和流程限制仍有效。详见随包 [Data API 合同](../../makedsl/references/DataAPIDesign.md#record-草稿保存约定)。

## 项目业务字段

复用语义一致的现有字段，否则为明确需要草稿的对象建一个普通业务字段。在项目可信配置中按 entityKey 显式登记状态 fieldKey、正常值、草稿值及适用消费者；不能根据中文字段名、是否有某个选项或浏览器开关猜测启用。未登记对象保持原行为。下面的 `saveState`、`normal`、`draft` 是示例，不能硬编码为平台字段或每个对象的默认约定：

```yaml
key: saveState
name: 保存状态
type: Make.Field.SingleSelect
meta:
  version: 1.0.0
properties:
  options:
    - label: 正常保存
      value: normal
    - label: 草稿
      value: draft
defaultValue: normal
```

`defaultValue` 与 `properties` 同级，单选写入使用 option **value 字符串**；读取沿用实际接口的单选对象/数组归一化，不把展示对象回写或仅按字符串判断资格。字段在新建、普通编辑、审批新建中不渲染输入，只在有读取权限的列表、手机卡片和详情中展示；表格单元格及批量编辑不允许手改。隐藏输入是 UI 规则，不是隐藏字段授权。Service 按操作意图生成状态，并验证当前普通 `createFields` / 普通更新字段白名单，或 BPM START 字段白名单；不能因字段由 Service 生成就绕过授权，也不能用可见 `fields` 代替 `createFields`。

普通新建的字段定义索引、载荷 key 校验、值序列化、默认值以及状态字段解析都从当前已授权的 createFields 建立；不能先用可见 fields 拒绝/丢弃 key，再检查 createFields。合法的可创建但不可读取字段仍应保存；读取集合保持独立，不因为创建需要就合并到全局可见字段。已有记录普通编辑与 BPM START 则各用其当前操作的权威定义及白名单。

绑定 BPM 时，新增字段后核查有效 START 配置是否允许该字段；未授权时报告配置缺口，不静默丢字段、改用普通 IAM 或擅自发布流程。TASK 授权保持独立。状态字段缺失、类型/选项不匹配或不可写时，停止依赖它的保存并给出明确错误。

## 写入协议与意图

先在宿主 `apps/docs/api.md` 约定 UI → Service 的 `isDraft` 查询参数及生成的状态；Service 验证后映射到 Make Record URL，保持原请求体、登录上下文、部署 appKey、Trace、取消与错误合同。不要把 `isDraft` 放进 Record 的 `data`，也不要伪造 SDK/CLI 未公开的选项。

| 用户动作 | Make 请求 | 业务状态 | 业务效果 |
| --- | --- | --- | --- |
| 新建/编辑“保存草稿” | Record Create/Update URL `?isDraft=true` | 同次 `data` 写入 `draft` | 持久化已填内容，允许必填缺失，不发起审批或正式业务效果 |
| 新建“保存” | Record Create，省略参数或 `false` | 同次 `data` 写入 `normal` | 完整校验后正常保存，不自动发起审批 |
| 已有草稿“保存” | Record Update，省略参数或 `false` | 完整校验后同次写入 `normal` | 对原 ID 转为正常保存 |
| “保存并提交” | 保留已确认的 Workflow 编排 | 创建/完整保存载荷显式写入 `normal` | 完整校验后发起；不能给 Workflow 编造 `isDraft` 参数 |
| 单元格、批量、附件、关系等局部修改 | 各自原接口；不扩展 `isDraft` | 不注入、不改变原保存状态 | 不因改一个字段把草稿转为正常保存 |

Make 直连创建示例（Service 根据运行模式选择网关前缀）：

```http
POST /api/make/data/v1/record?isDraft=true
X-Make-Target: MakeService.CreateResource
Content-Type: application/json

{"appKey":"<deploy-app-key>","entityKey":"document","data":{"title":"待补充","saveState":"draft"}}
```

已有草稿的正常保存示例：

```http
POST /api/make/data/v1/record?isDraft=false
X-Make-Target: MakeService.UpdateResource
Content-Type: application/json

{"appKey":"<deploy-app-key>","entityKey":"document","recordID":"<original-id>","data":{"title":"完整内容","saveState":"normal"}}
```

示例对象仅有 title 需要填写；实际转换必须满足该对象**整条记录**的必填条件。普通 Update 只校验已提交字段，`isDraft=false` 不会自动补验未提交字段。Service 必须根据当前已授权的可信记录/保存上下文及本次补丁构造有效快照，完成全量必填和业务完整性校验后再保存 `normal`；或者使用后端已确认的原子完整性校验接口。不能只 PATCH 状态即宣布转正式；关系和附件的最终有效值也需纳入。不新增普通记录读取权限要求，也不使用高权限账号代读；创建使用已授权提交和已核实的创建默认值，字段权限不足以证明完整时报告缺口，不代填或扩大授权。

不要先保存业务内容再单独 PATCH 状态。内容与状态尽可能在同一授权写入中提交；若业务还涉及多步附件、关系或流程，沿用原部分成功/结果未知恢复合同，明确每步完成情况。更新、重试和转正常都复用已保存 ID，不重新创建草稿。

多接口写入若不能原子完成，须明确正式业务可消费的完成边界；不能在必要附件/关系仍未完成时，就让中间的 normal 记录触发正式业务效果。优先使用已确认的原子编排或后端完结保障；没有对应能力时说明该路径的隔离缺口，保留原部分成功恢复，不发明事务参数或声称整单已经原子完成。

Service 拒绝用户直传状态与动作矛盾、非法枚举或局部编辑试图改状态；生成值不接受客户端覆盖。允许正常记录退回草稿前，应核查它是否已发起审批、记账、付款、扣减库存或被下游消费；已有正式效果不能只靠改标识撤销，保留原禁编及冲销/撤回规则。

所有纳入该业务的导入、复制、集成及直接 API 客户端都要遵守同一状态写入约束。直接调用 Make Record `isDraft=true` 却省略业务状态时，平台仍可能补默认 normal；平台不会替项目将其改成 draft。若需要跨客户端保证，由实际拥有写入校验职责的后端入口约束参数与业务状态一致，不能只校验浏览器请求。存在未纳管写入口时，明确指出状态标记可能不可靠及受影响的正式能力，不能将正常默认值视为已经完成所有来源的草稿识别。

## 排除草稿的业务范围

为每个启用草稿的对象明确“正式业务数据”的资格，并在拥有该业务能力的可信后端实施。一般使用已确认正常值的**允许列表**，示例为 `saveState in ['normal']`；不要使用 `saveState != 'draft'` 将 null、缺失或未知值误当正式数据。保存状态正常只是必要条件，仍需叠加原审批、有效期、删除及权限等条件。

字段默认值不回填历史记录，也不在读取或聚合时把历史 null 变成 normal。接入前统计历史空值及来源，给出显式迁移或单独核实的兼容方案；未经确认不批量改旧记录，不直接把空值纳入正式口径。未知状态在正式业务中排除并反馈依赖缺口。正式口径切换前完成历史分类、覆盖范围和指标对账，不能直接启用过滤而使旧数据静默退出统计；未完成时明确标记受影响能力尚未就绪。

| 入口/能力 | 必须检查的排除点 |
| --- | --- |
| 指标卡、图表、报表、同比环比、排名、统计接口 | 在聚合前过滤；count、sum、avg、最值、去重人数、比率的分子和分母、基期及比较期都使用同一业务资格 |
| 分组、分页、总数、下钻、导出、打印 | 正式业务视图的组、叶子、total、汇总、明细、跨页选择及导出保持一致；不能先分页/聚合再从结果中过滤草稿 |
| 多实体分析、Lookup、关系、Rollup、Count、Formula、缓存指标 | 检查每个参与的源/目标对象、子查询、关联成员、派生输入和预计算结果；只过滤主表不能消除草稿子记录的贡献 |
| 业务候选与引用 | 订单、付款、报销、核销等正式动作的候选不得选草稿；提交时重新检查引用对象，防止候选加载后状态变化。人员/部门等无草稿能力的基础数据不额外过滤 |
| 首次发起、批量提交及审批恢复 | 草稿不直接发起；先按原 ID 完整校验并正常保存。发起前重查业务资格，不能仅判断 `UNSUBMITTED`。已在流程内的记录保留原锁及节点授权 |
| 预算占用、库存、财务分录、余额、额度、结算、付款 | 排除草稿与其关联贡献；不要以必填不全或金额零推断草稿。已有正式效果的降级须遵循显式补偿策略 |
| 保存回调、触发器、定时/批处理、外部同步、Webhook、通知 | 真正执行处检查最新状态；草稿保存事件仍可到达。正式业务副作用排除草稿；草稿自己的保存审计和用户明确需要的草稿提醒可保留 |
| 搜索索引、数据仓库、BI、订阅、ETL、AI/RAG/工具数据 | 生产业务检索和分析源排除草稿，包括摘要、向量、离线快照和历史缓存；状态变化时更新/失效已有投影，不能只改前端提示词 |

Make 本次能力**不提供全局草稿过滤开关**。内置 Rollup/Count 或外部平台没有资格过滤能力时，不宣称自动排除；改用已授权、可证明等价的 Service 查询计算，或在用户确认成本与范围后建立独立正式数据投影。能力未落实时禁用/标明受影响的正式指标或业务动作，不能继续输出受污染结果。只修改应用 Service 不能拦截直接调用平台的其他客户端或平台保存回调；逐一登记实际消费者及其责任边界，缺少对应后台接入能力时报告缺口，不伪装成已经全局隔离。

## 查询、批量与直接动作

- 草稿管理列表/详情保留原读取权限，可以展示草稿并标识状态；“所有记录”总数可以包括草稿，但不能冒充正式业务统计。草稿数量属于明确的管理指标，需与正式指标分开标注。
- 资格条件与原搜索、用户筛选、对象/行权限按 AND 组合，`groupFilter` 保持独立并由后端共同限定结果；分别保留括号及原表达式结构，不用条件覆盖另一条件。用已确认的表达式验证/构造器和字段类型合同，不能插值拼接未校验的 CEL。原用户 filter 作为逐字不透明子表达式保留，必要时只在外层组合资格，不重新序列化、trim 或扁平化；原 Preset 和 groupFilter 不被改写。这是正式业务接口的后端资格附加，普通管理接口继续原样透传。用户清空筛选、OR 条件或 Preset 都不能撤掉后端强制业务条件。
- 将资格条件用于 Make 查询，在分页、分组和聚合前执行。明细、total、导出、缓存 key、下钻和跨页全选沿用同一可信范围。缓存隔离租户/用户/App/权限代际、查询和资格策略，状态转变后使相关结果失效。
- 修改单元格、继续编辑或删除草稿本身可以按原权限允许；不把所有草稿操作一律禁用。正式批量业务动作对显式 ID 集合逐项验证，发现不合资格则按明确合同拒绝/反馈，不能静默缩小用户选择；select-all 的预检与执行使用同一附加资格范围，保留一请求批量及原授权合同。
- 单条 URL、直接发起/付款/同步接口、后台任务及可调用工具也执行资格检查，不能只依赖列表不可见。客户端不得用 `includeDrafts` 绕过正式业务条件；草稿管理是单独、已授权的业务入口。
- 在真正执行副作用时重查，使用现有事务、版本/并发保护及幂等设施；未具备原子保护时明确竞态限制，不宣称“先查再写”已经解决并发。重试不重复占用预算、发起流程、付款或同步；不要自行发明平台不支持的参数。
- 平台默认仍运行唯一约束、编码生成、关联维护和保存回调。草稿可能占用唯一值或编号，不承诺连续编号或保存草稿完全没有平台内部效果；业务自己的消费方必须落实上述门槛。

## 验证与交付

先确认用户要求、对象及资格映射，再实施 UI/模型/Service/消费者。读取原数据流，列出实际存在的每个消费者及其落实位置；不能把本表当作所有项目都要新建的功能清单。

至少验证：无草稿需求零新增；缺必填可保存草稿但非法日期等仍失败；正常保存草稿缺必填失败且状态不变；补齐后同 ID 变 normal；普通局部修改保持原状态；授权缺失/锁定/流程运行不能绕过；普通确定未写入的校验失败后保留输入可修正再保存，未知写入及合并提交部分成功仍按原恢复合同保护。

对数据口径使用同时含正常、草稿、历史 null/未知及无权记录的夹具，验证分页 total、分组、指标分母、关联草稿、导出、全选、直接动作、异步回调和状态变化缓存失效；记录落地消费者与尚未覆盖的范围。仅技能文本检查通过，不能声称宿主应用、后端回调、外部 BI 或真实审批已经完成联调。

字段默认值遵循 [默认值合同](../../makedsl/references/FieldDesign.md#字段默认值--default-value)，应用前 diff，应用后读回元数据并验证缺 key 创建的实际值。环境/CLI/转换层未保留 `defaultValue` 时报告能力缺口；动作生成的 normal/draft 仍需显式提交，但不能拿它冒充平台默认值已生效。
