# 后端业务错误文案

本合同用于已确认面向浏览器的 Make 公共业务错误响应。Service 透传边界见 [Service 错误合同](../../make-app-service/references/service-layering.md)。认证失效、已确认的权限拒绝、AI 专用错误协议仍由对应 Skill 处理，不因本合同另建请求通道或改变成功码。

## 文案与错误分类

- 宿主先按接口合同判断 HTTP 状态和业务成功码。失败时优先提取非空字符串 `msg`；该字段缺失、空白或非字符串时，才按已确认接口兼容 `message`。未知业务错误码不能使有效公共原因丢失。
- 将原因作为普通文本交给现有统一错误出口，保留具体原因和接口已提供的处理联系人。不得按错误码覆盖有效 `msg`，不得只允许两三条固定文案；不能按长度、中文关键词、SQL 单词、尖括号或 URL 猜测业务文本是否可展示。长内容按组件滚动/换行合同处理，不能渲染为 HTML。
- 两个公共字段都不可用，或没有可解析的公共错误体时，才使用宿主的错误码说明或通用兜底。不要 stringify 完整响应、嵌套对象、`error`、`stack` 或 SDK 原始 `Error.message`。
- HTTP 2xx 业务失败为 `business`，非 2xx 为 `http`，没有响应的网络失败为 `network`。错误分类、业务码、实际 HTTP 状态和本次 Trace ID 分别保留；HTTP 5xx 有有效公共原因时也不能仅显示“请求未能完成”。
- 操作建议可放到说明区，不替换失败原因。文案提取不决定权限、失败是否落库、任务是否执行、能否重试或重复创建；这些仍由对应业务合同判断。后端文案包含“重试”也不授权自动重发。

## 安全边界

“不展示原始错误”指未经协议确认的 Error 对象、内部堆栈、诊断正文、凭据等，不是拒绝展示后端公共 `msg`。宿主只提取已确认协议的公共字段，错误正文和联系人不进入通用请求日志。

如果已发现公共 `msg` 混入内部堆栈、token 或其他敏感信息，说明后端公共错误合同失效：要求后端修复并阻止受影响链路发布，不用前端正则或固定文案白名单掩盖问题。普通 HTML 网关错误页也不是公共业务 `msg`。

## 提取示例

以下是宿主纯函数示例，不是 npm 包导出。调用前由现有请求层识别失败响应和公共协议；不同接口的成功码、权限拒绝结构和恢复规则不由本函数推断。宿主已有等价 helper 时直接修正它，不新增并行错误通道。

```js
export function readPublicBusinessMessage(payload) {
  if (!payload || typeof payload !== 'object' || Array.isArray(payload) || payload instanceof Error) {
    return undefined;
  }
  return [payload.msg, payload.message].find(
    value => typeof value === 'string' && value.trim().length > 0,
  );
}
```

示例输入 `{ code: 41000022, msg: "未找到下一环节审批人，请联系审批管理员甲配置" }` 应保留该原因。同一 code 的下一次响应改为另一原因或联系人，显示内容也必须随响应变化。

## 宿主验收

使用真实请求适配器与错误出口，模拟 HTTP 响应，不只 mock 已转换的最终错误对象：

1. HTTP 200 业务失败、HTTP 4xx/5xx 的有效公共错误均显示原原因、实际状态、业务码和 Trace；只提示一次，不自动重发。
2. 同一 code 的不同原因/联系人、未知 code、有 `msg` 和 `message` 的优先级、长文案、普通尖括号文本均保留；缺失/空白/非字符串公共字段走兜底，不展示对象或堆栈。
3. 无响应网络异常、认证失效、已确认权限拒绝保持原流程；通用日志不打印公共原因、联系人或响应正文。
4. 覆盖发起、办理、撤回等当前改动涉及的入口；保留业务恢复和防重复写入测试，特别是 5xx 展示具体原因后仍不能推断未执行。

仓库的示例测试执行上面的函数验证提取行为；它不能替代目标 App 的请求到卡片链路验证。
